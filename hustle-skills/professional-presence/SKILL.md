# Professional Presence

Improve Pon's public professional presence using verified public evidence. Prepare
exact previews first. Perform live account actions only while Pon is present and
after he approves that exact action.

## Non-negotiable boundaries

- Exclude personal data that is not required for the approved action, credentials,
  precise location or routines, private conversations, and private deliberations.
- Exclude employer, customer, workplace, private-repository, non-public analytics,
  and unreleased information in every language, including Thai.
- Never invent experience, student status, eligibility, results, testimonials,
  project activity, issues, releases, or credentials.
- Use public personal repositories and Pon-approved portfolio artifacts as evidence.
- Treat uncertainty as a stop condition. Ask Pon or omit the claim or field.
- Let Pon enter passwords, MFA codes, payment details, and government or student ID
  numbers himself. Never expose them in chat, notes, screenshots, or logs.

## Choose the workflow

### LinkedIn profile

Audit headline, About, experience, education, skills, Featured, projects, photo,
and banner. Recommend only changes that improve recruiter understanding. Use only
Pon-supplied photo or banner assets.

Show one review packet containing, for each section:

- current text;
- proposed exact text;
- public evidence and rationale;
- `Approve`, `Edit`, or `Skip`.

Apply only approved sections while Pon watches. Treat each live edit as a separate
action. Verify the public result afterward while logged out when possible.

### Weekly post

Scan only public personal repositories and approved portfolio artifacts. Present
up to three strong topics. Skip the week when no verified work is worth sharing.

Use this exact structure:

1. One clear problem
2. What you built
3. Practical result
4. Takeaway
5. One public URL or visual

Show the exact text, media preview, URL, audience, evidence/privacy result, and
recruiter benefit. Publish only after Pon says `Publish this exact version` while
watching. Verify the live URL publicly and record the result privately.

### LinkedIn comments and messages

Check only during an attended weekly session or when Pon asks. Draft the exact
reply first. Send only the exact reply Pon approves while he watches. Never monitor
or reply in the background.

### GitHub profile

Audit the public profile README, bio, pinned repositories, project READMEs, and
genuine release or portfolio documentation. Recommend pins using job relevance,
verified results, README/demo/test quality, recency, privacy, and portfolio variety.

Prepare changes locally and show the exact diff plus rendered preview. Commit,
push, edit the bio, or change pins only as separately approved live actions while
Pon watches. Verify the logged-out public result. Never manufacture activity.

### Free learning and student opportunities

During an attended LinkedIn review or when Pon asks, notice legitimate offers such
as free learning resources, courses, AI tools for students, scholarships, credits,
certification vouchers, or education access programs. Do not run unattended
monitoring.

Read [student-opportunities.md](references/student-opportunities.md) before
researching an offer, filling a form, or writing an access-request email.

## Mandatory live-action gate

Before every public edit, post, comment, message, form submission, email send,
commit, push, bio edit, or pin change:

1. Run a secret and personal-data scan, including Thai and English names for any
   employer or customer that must remain private.
2. Check for local paths, hidden Git history, private URLs, metadata, and attached
   files that could leak information.
3. Show the complete action packet: destination, exact values/text, attachments,
   audience or recipient, source evidence, and privacy result.
4. Wait for explicit approval of that exact version. Approval to research, draft,
   or fill fields is not approval to submit, send, publish, commit, or push.
5. Execute only while Pon is present, then verify the result from the public or
   recipient-facing view when possible.

Stop if the destination changes, the page adds fields, the content changes, the
session expires, or verification is uncertain. Build a new packet and ask again.
